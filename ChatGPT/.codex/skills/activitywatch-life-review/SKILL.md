# ActivityWatch life review

## Choose the mode

- Bare `$activitywatch-life-review` (including a skill attachment with no additional user request) or an explicit setup/repair request means **setup**: read [setup](references/setup.md), check prerequisites, and create/reuse this computer's authorized daily review. The user's standing preference is to use the current computer by default without asking which computer owns the daily schedule. Preserve an existing local task and manual pauses. Do not generate a habits review in setup mode.
- An explicit review request or authorized scheduled review means **review**, even if its prompt only says to run the skill. Do not create/repair schedules as a side effect of a review.

## Discover this computer

Use the Browser plugin in the ChatGPT in-app browser (`iab`). Start at `http://127.0.0.1:5600/#/`, or the user's explicitly supplied local address. Read the displayed server Host and Activity navigation link; follow visible controls to identify the matching local data host. Never construct a route with a saved computer's hostname. If multiple/imported hosts make the local stream ambiguous, ask which to use. A previously selected remote host is not proof of the current computer.

Follow the discovered **Window**, **Browser**, and **Timeline** links. The root may redirect to a default view; for review, switch straight to Window without analyzing Summary. Do not query the API, read the ActivityWatch database, or use shell HTTP for discovery or review. If the local page or Browser plugin is unavailable, report the missing prerequisite and stop browsing; never fabricate historical data.

## Personal priorities

The user describes a good day as making time for English learning, walking, coding in VS Code, and useful work with Codex or ChatGPT. They want to avoid Bilibili and games, and reduce videos that are not in English. The user says their YouTube viewing is for learning English: count observed YouTube time as English-learning time in reviews, without needing to infer the video language from its title. The user says Bilibili viewing is not English learning: do not count Bilibili time toward that goal, even when a video title show with English content. If a future review suggests otherwise, ask rather than silently reclassifying it. Use these as their own stated priorities when interpreting patterns, without assuming every app name or video title proves a category. Walking and offline study may not appear in ActivityWatch; ask about them instead of treating untracked time as failure. Keep advice flexible and respect rest, social time, and changing priorities.

## Review workflow

1. Interpret the requested periods in the user's local timezone. By default, review both **yesterday** (the most recent completed local calendar day) and **ActivityWatch's most recent 7 days** (the seven-date range ending with today, including today's activity recorded so far). State the displayed dates and label the seven-day range as in progress when today is included. Do not substitute a fixed Monday–Sunday calendar week. If the user explicitly requests another period, follow that request.
2. Discover the current host as above through `mcp__cua_repl.js`. Open a hidden tab with `cua.createBrowserTab("iab", url, { visible: false })` and reuse it for the review. Read each page with `tab.getAXState()` or the Browser plugin's DOM snapshot after navigation; opening a URL alone is insufficient. Use Browser plugin actions for date controls and **Show more**. Do not switch to the user's default browser, use shell HTTP requests, or query the ActivityWatch API directly. If ActivityWatch cannot be inspected in the ChatGPT browser, report the access failure and stop.
3. Start on **Window**, without opening Summary. Select **day** and yesterday's local date for the daily review; verify its displayed range runs from yesterday to today. For the weekly review, select **7 days** anchored on today's local date; verify that its displayed query range starts six dates before today and ends tomorrow. This is ActivityWatch's recent seven calendar dates, including today so far; do not select **week** or anchor **7 days** on a Sunday. Reuse the same tab and switch between **Window** and **Browser** for each period. Visit the separate **Timeline** page once per period, setting its date range to the displayed period boundaries and checking only activity recorded through the run time for the in-progress seven-day range. For an explicitly requested period, use only that period. Do not reload or revisit a page whose visible data is already sufficient.
4. Read the period's active-time total from the Window or Browser header, then inspect **each list separately**: Window's Top Applications and Top Window Titles; Browser's Top Browser Domains, Top Browser URLs, and Top Browser Titles. Each list has its own **Show more** control. For each list, click its control repeatedly, re-read that list after each click, and continue until a row under **30 minutes** is visible or that list has no further expansion or pagination. Do this for both the day and week; one click or one expanded list does not complete the page. If the UI stops at a row of 30 minutes or more, report that the shorter rows were unavailable. Use the expanded rows to identify relevant games, Bilibili, YouTube, coding, and ChatGPT/Codex activity; omit unrelated sensitive titles and raw URLs from the answer.
5. On Timeline, inspect the time axis and activity blocks for long AFK gaps spanning the night or early morning; avoid reading or printing its full event list when a focused visual inspection answers the question. The user says such long overnight AFK stretches mean they are sleeping, so count their visible duration as sleep without asking them to confirm each time. If the display cannot establish a gap's boundaries, say the sleep duration is unavailable instead of guessing.
6. Compare Window, Browser, and Timeline without adding overlapping browser and window durations. Distinguish observed computer activity from untracked time; ActivityWatch does not establish exercise, mood, or all work. For a long overnight or early-morning AFK stretch, report the visible start, end, and duration as sleep under the user's stated rule; call the times approximate when the timeline resolution is imprecise. Do not classify unrelated short or daytime gaps as sleep solely because the computer was inactive.
7. End with a concise summary table for each reviewed period: normally one daily table and one weekly table. In each, pair observations with practical advice across the user's relevant priorities: games, YouTube as English learning, Bilibili, coding, useful ChatGPT or Codex work, sleep, and walking or offline activity when known. Do not invent data for an untracked area. Include approximate durations where useful, and name specific recorded games, videos, or activities when they help explain a pattern. Distinguish exact titles from inferred categories and say when titles are unavailable. Keep the tables focused rather than listing every item. Separate observations from hypotheses, and give a few small, supportive suggestions tied to the patterns. Ask about context when it would change the advice.

## Privacy and access

Activity titles and URLs may be sensitive. Minimize what is opened and repeated, and include relevant recorded titles when the user asks for specific games, videos, or activities, while avoiding unrelated sensitive titles, raw URLs, and raw logs. Do not send ActivityWatch data to an external service or person. If access through the ChatGPT in-app browser fails, explain the problem and stop; do not infer findings from the page links alone or use a different browser or non-browser substitute without the user changing this preference.

Bare/setup invocation includes the user's standing request to initialize the daily review under the setup reference's duplicate checks. Ordinary reviews do not authorize a new recurrence. Never create worktrees.
